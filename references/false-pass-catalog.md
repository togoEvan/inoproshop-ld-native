# 「0 错误」的八种假象 —— 假通过目录

> 这份文件只记**一种错误**：验收给出 PASS，但实际没验证到东西。
> 每条包含：现象 / 根因 / 怎么认出来 / 怎么修。
> 判断标准一句话：**验收器只防它建模的那一个维度；没建模的维度它一定放行。**

---

## 速查表

| # | 假象 | 一句话根因 | 识别信号 |
|---|---|---|---|
| 1 | 没挂进任务也 0 错误 | 未挂进任何任务的 POU 不参与编译 | 新建对象后 build，错误数一条没变 |
| 2 | 脏容器里怎么错都 0 错误 | 设备未安装 / 库占位符缺失时编译器提前退出 | 消息里出现「设备未安装」「占位符库」 |
| 3 | 错误数被截断 | 每分类每 severity 有上限（error 500 / warning 100 / message 100） | 消息末条「多于N个错误/警告：跳过更多的…」 |
| 4 | 分类不存在，读成 0 条 | 消息分类按需注册，没 build 过就没有编译分类 | 分类清单里少 97f48d64 / 217bc73e |
| 5 | severity 读不到被当普通消息 | 采集侧静默降级成 "?"，判据只认字面 "error" | 明明有错却 PASS，明细里 severity 是 ? |
| 6 | 验收器恒 PASS | 解析器跟不上真实结构 / 只建模了部分维度 | 换一个尺寸的输入，签名一模一样 |
| 7 | 负样本自己变成正样本 | 改错了地方（把声明也改了，或改进了注释） | 故意写错却 0 错误 |
| 8 | 基线被别人清空 | `system.clear_messages` 是**进程级**的 | 错误数突然从 N 回到 0 |

## 1. 没挂进任务也 0 错误

**现象**：新建 `prg_XXX`，故意写一个不存在的标识符，`app.build()` 返回 0 错误。

**根因**：InoProShop 只编译**被任务调用**的对象。挂在 Application 下的 POU 不进编译单元。

**复现**：

1. `app.create_pou(...)` 建 POU，写入 `x := bNoSuchSymbol;`；
2. 不挂任务 → build → 0 错误；
3. `main_task.pous.add(name)` → build → 立刻报「没有定义标识符'bNoSuchSymbol'」。

**修**：把「挂载」做成导入流程里的一等步骤，并用**前置断言**而不是事后检查：
枚举所有任务（`Task Configuration` → 每个 task 的 `.pous`），确认目标名在其中，
不在就直接 FAIL 并提示「未挂进任何任务，双分类 0 错误是假通过」。

## 2. 脏容器里怎么错都 0 错误

**现象**：往一个模板工程里写 120 个未定义标识符，build 出来的 error 数一条没变。

**根因**：工程缺设备描述或缺库（`#IoStandard` 这类**占位符库**没装）时，编译器在「设备未安装，不能生成代码」之后就退出了，**根本没走到语义分析**。

**识别**：消息里出现 `设备未安装，不能生成代码。` / `占位符库 'X' 不能被处理` / `没有定义接口 'ICmpEventCallback'`。

**修**：验证语义前先确认「能走到语义分析」——用一条已知必错的负样本探一次；探针不报错就说明容器脏，换干净副本。

---

## 3. 错误数被截断

**现象**：编译 0 错误，但明明写了 1300 个错。

**根因**：消息池按 **severity 分别限额**：

| severity | 上限（本机实测） | 提示行 |
|---|---|---|
| Error | 500 | `多于500个错误：跳过更多的错误信息` |
| Warning | 100 | `多于100个警告发生：跳过更多的警告信息` |
| Message/Information | 100 | `多于100个消息发生：跳过更多的消息信息` |

**关键顺序**：池子是**时间正序**（旧的在前），截断吃掉的是**最新的**消息 —— 所以「新增错误在末尾」这件事在高基线工程上必然丢。

**修**：

- 判据改用**结构化计数**：`get_message_objects(category, Severity.Error)` 的长度按**完整池**过滤，不受截断影响；
- 或做**双快照差分**（导入前 / 导入后各读一次，比净增量），baseline 自动归零；
- 无论哪种，检测到提示行就**降级为 UNKNOWN**，不允许判 PASS。

## 4. 分类不存在，读成 0 条

**现象**：脚本读 `97f48d64`（编译）得到 0 条，判「0 错误通过」。

**根因**：消息分类**按需注册**。没 build 过的会话里根本没有编译分类；某次实测只有 2 个分类（预编译 + 导入导出），另一次有 6 个。GUID 集合随版本与操作历史变化。

**修**：读之前先枚举 `system.get_message_categories()`；缺关键分类就**主动 build 一次再读**（单次调用，不 sleep 不轮询）；仍缺 → 判 UNKNOWN，**不得当 0**。

---

## 5. severity 读不到被当普通消息

**现象**：构造一条 `severity = "?"` 的新增错误，双快照差分给出 PASS。

**根因**：采集侧 `prop()` 用 try/except 吞掉异常返回 `None`，写入快照时变成 `"?"`；判据只把字面 `"error"` 计为错误。于是「不知道」被伪装成「没问题」。

**修**：采集侧**取不到 severity 就 raise**（宁可不产快照，也不产坏快照）；判据侧再扫一遍 `"?"`，命中即 UNKNOWN。

---

## 6. 验收器恒 PASS

**两个实例**：

- **解析器跟不上真实结构**：结构是 `NetworkItems → 分支组 → Trees`，解析器只下钻一层，把内层分支读成空，所有网络签名都还原成 `<= TRUE` —— 无论输入是什么，比对结果都「一致」。
- **只建模部分维度**：逻辑比对只看拓扑（谁连谁），不看线圈类型位（置位 S / 复位 R）——把 `S` 改成 `R`，状态机永远进不了该状态，逻辑比对仍 PASS。同理，`IsContact` 语义（值引脚被写成触点）编译器也不校验，全链路 PASS。

**修**：每个维度都要有**专门的负样本**，改一处、期望 FAIL、实测 FAIL，才算这一维被覆盖。

| 维度 | 负样本造法 | 期望 |
|---|---|---|
| 拓扑 | 删一条支路 | FAIL |
| 线圈类型 | S 改 R（`Operand.Flags` 2 ↔ 3） | FAIL |
| 值引脚形态 | `IsContact` False → True | **编译器不报**，需静态检查器自己的规则 |
| 边沿 | 去掉 `InputFlags[0]=16` | 编译器不报，需行为仿真或人眼 |

## 7. 负样本自己变成正样本

**现象**：把 `iGoodCnt` 全替换成 `iGoodCntNOPE` 造负样本，build 出 0 错误。

**根因**：替换把**声明行**也改了（`iGoodCntNOPE : INT;`），于是它变成合法标识符。

**修**：负样本**只改引用、保留声明**。造完先自检：目标名在声明区出现次数应为 1（就是它自己），在实现区应 ≥1。

同类陷阱：改到注释里的同名文字、改到字符串字面量里 —— 都不产生错误。

---

## 8. 基线被别人清空

**现象**：错误数从 101 突然回到 0，看起来「修好了」。

**根因**：`system.clear_messages()` 是**进程级**的，不是脚本级。同一 IDE 进程里两个工具/两个 agent 各自清消息，会互相抹掉对方的基线。

**修**：

- 不要 clear。要干净基线就**重启 IDE 或新建工程**；
- 做差分就不要清空（清空等于把 before 也删了）；
- 多 agent 共用一个 IDE 时，约定**唯一持有者**（锁文件记 PID + 心跳），其余只读。

## 元规则（比上面八条更重要）

1. **验收器只防它建模的那个维度**。补验收器 ≠ 补任何维度；补的是「这一维的负样本 + 判据」。
2. **凡是读取器，都有容量与可用性边界**。分类可能不存在、条数可能被截断、字段可能取不到；「读到 0 错误」必须同时证明「读取器完整可用」。
3. **自己造的样本不能自证**。同一个 agent 造样本 + 自己判通过 = 循环论证。要么用**用户/真实工程的现成样本**，要么用**独立的第二套判据**（行为仿真、人眼、另一个实现）。
